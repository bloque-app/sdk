# Passkey approvals for cards, accounts and API keys

A person approves, with their own passkey, every operation they start that moves money, creates or unlocks a way to spend, or changes an account or a credential. The approval happens on Bloque's identity portal (`approvalUrl`). Your app never handles the passkey: it shares the link, waits for the approval, and repeats the same call with it.

The general flow, error types and `withApproval` are described in [Getting started → Passkey Approvals](../start/getting-started#passkey-approvals). This page lists the card, account, BRE-B key and API-key methods that take an approval, and the points that differ from transfers.

## Which methods take `approval`

Each method below takes an `options` argument with `approval` (the value `waitForApproval()` returns). Account creation takes it in the existing `CreateAccountOptions`, next to `idempotencyKey`.

| Method | Why it needs the owner |
|---|---|
| `accounts.card.create(params, options)` | Issues a new card: a new way to spend the balance |
| `accounts.card.activate(urn, options)` / `updateStatus(urn, 'active', reason, options)` | Unfreezes a card: spending is possible again |
| `accounts.card.update(params, options)` | Can change the PIN |
| `accounts.card.updateMetadata(params, options)` | Changes which balance purchases debit, spending rules and cashback destinations |
| `accounts.card.tokenizeApple(urn, params, options)` / `tokenizeGoogle(urn, params, options)` | Adds the card to a phone wallet |
| `accounts.card.delete(urn, options)` | Deletes the card |
| `accounts.virtual`, `polygon`, `bancolombia`, `us`: `create(params, options)`, `updateMetadata(params, options)`, `activate(urn, options)` | Opens, changes or unfreezes an account |
| `accounts.virtual.delete(urn, options)` / `accounts.polygon.delete(urn, options)` | Deletes an account |
| `accounts.us2.create(params, options)` / `accounts.externalUsBank.create(params, options)` / `externalUsBank.exchangePublicToken(params, options)` | Opens an account or links an external bank |
| `accounts.breb.createKey(params, options)` / `activateKey(params, options)` / `deleteKey(params, options)` | A BRE-B key decides where deposits land, and can forward them to a wallet |
| `identity.apiKeys.create(params, options)` / `identity.apiKeys.rotate(id, options)` | Mints a credential that acts as the person |

Freezing and disabling (`card.freeze`, `card.disable`, `breb.suspendKey`) never ask for an approval: a lost card must be stoppable at once. Renaming (`updateName`) does not either.

Whether a call asks for an approval is decided by the API's approval gate, not by the SDK, and depends on the mode the deployment runs it in: in `off` or `shadow` it refuses nothing, and in `enforce` it asks the person who owns the account (today, individuals; not businesses or service-to-service calls). Pass `approval` only when repeating a call that was refused with `BloqueApprovalRequiredError`.

## Example: issue a card

```typescript
import { BloqueApprovalRequiredError, withApproval } from '@bloque/sdk';

const card = await withApproval(
  (approval) =>
    bloque.accounts.card.create(
      { name: 'Groceries' },
      { idempotencyKey: `card-${orderId}`, approval },
    ),
  {
    onApprovalRequired: (error: BloqueApprovalRequiredError) => {
      // Show the owner what they approve (error.summary), then the link.
      notifyOwner(error.approvalUrl);
    },
  },
);
```

Keep `idempotencyKey` the same on the repeat: the approval covers the operation's fields, and the key makes a repeat after a lost response land on the same card.

## Example: change spending rules

```typescript
const update = (approval?: string) =>
  bloque.accounts.card.updateMetadata(
    { urn: cardUrn, metadata: { priority_mcc: ['5411'] } },
    { approval },
  );

const updated = await withApproval(update, {
  onApprovalRequired: (error) => notifyOwner(error.approvalUrl),
});
```

Repeat the call with exactly the same parameters. A different PIN, metadata value or status is a different operation and needs a new approval.

## BRE-B keys

`breb.createKey`, `activateKey` and `deleteKey` return their errors as `{ data: null, error }`, except the passkey-approval errors (`BloqueApprovalRequiredError`, `BloqueApprovalInvalidError`, `BloqueApprovalExpiredError`, `BloqueApprovalUnavailableError`), which are **thrown**, as on every other gated method. That lets you wait for the approval and repeat the call:

```typescript
const key = await withApproval(
  (approval) =>
    bloque.accounts.breb.createKey(
      { keyType: 'BCODE', key: '0016027228', ledgerId },
      { approval },
    ),
  { onApprovalRequired: (error) => notifyOwner(error.approvalUrl) },
);
if (key.error) {
  // Any other refusal, returned as before.
}
```

## Redirect to approve and come back

`withApproval` and `waitForApproval()` keep the request in memory while the owner approves, so they need your page to stay open. When you send the owner to `approvalUrl` with a full-page redirect instead, your page is gone when they return: save the pending approval first, then collect it and repeat the call on the way back.

1. Call the operation with `approvalReturnUrl`, where the approval page sends the owner once they approve. Every method that takes `approval` takes it too.
2. On `BloqueApprovalRequiredError`, save `error.toPendingApproval()` together with the call's parameters, then redirect to `error.approvalUrl`.
3. On `approvalReturnUrl`, call `approvals.collect(pending)` and repeat the same call with the approval it returns.

```typescript
import {
  BloqueApprovalExpiredError,
  BloqueApprovalRequiredError,
} from '@bloque/sdk';

const RETURN_URL = 'https://myapp.com/transfers/approved';

// 1–2. Before the redirect
try {
  await user.accounts.transfer(params, {
    idempotencyKey: paymentId,
    approvalReturnUrl: RETURN_URL,
  });
} catch (error) {
  if (!(error instanceof BloqueApprovalRequiredError)) throw error;
  sessionStorage.setItem(
    'pending-transfer',
    JSON.stringify({ params, paymentId, pending: error.toPendingApproval() }),
  );
  if (error.approvalUrl) window.location.assign(error.approvalUrl);
}

// 3. Back on RETURN_URL
const saved = JSON.parse(sessionStorage.getItem('pending-transfer')!);
let approval: string;
try {
  approval = await user.approvals.collect(saved.pending);
} catch (error) {
  if (error instanceof BloqueApprovalExpiredError) {
    // Expired or already collected: it can never succeed, so drop it.
    sessionStorage.removeItem('pending-transfer');
  }
  // Anything else keeps the saved state: BloqueApprovalPendingError (offer
  // saved.pending.approvalUrl again; this page runs again when they return),
  // or a network error, timeout, 503 or 429 (call collect() again).
  throw error;
}
// Remove it only now: until collect() succeeds the owner can still approve.
sessionStorage.removeItem('pending-transfer');
await user.accounts.transfer(saved.params, {
  idempotencyKey: saved.paymentId,
  approval,
});
```

- `approvalReturnUrl` must be an absolute https URL whose origin your origin allows, or the call throws `BloqueReturnUrlNotAllowedError` (400). A value that is not an absolute URL, or has spaces or control characters, throws `BloqueConfigError` before anything is sent; non-ASCII characters are percent-encoded. Bloque sets the allowed origins on your origin (`tos_gate_return_url_allowlist`, the same list as the TOS gate).
- The operation runs once: `collect()` hands out an approval only once, and the API refuses an approval that was already used. A second `collect()` throws `BloqueApprovalExpiredError` with `reason: 'approval_delivered_elsewhere'`.
- Repeat right away. The owner's approval lasts about two minutes from when they open the approval page:
  - not collected in time: it is dropped, and `collect()` throws `BloqueApprovalPendingError` (or, after `expiresAt`, `BloqueApprovalExpiredError` with `reason: 'approval_not_received'`, without calling the API);
  - collected, but the repeated call arrives too late: that call throws `BloqueApprovalExpiredError` (403).

  Either way, nothing moved: repeat the call without `approval` to get a new link.
- If the response to `collect()` is lost (a timeout, the tab closes) after the API handed out the approval, the next `collect()` throws `approval_delivered_elsewhere`. Nothing moved; request a new approval.
- `approvalUrl` can be missing on deployments without an approval page; check it before redirecting.
- The approval page adds nothing to `approvalReturnUrl`: `collect()` is how you learn whether the owner approved.
- `pending.approvalToken` and `pending.approvalUrl` can only collect this one approval (the owner still signs with their passkey), but keep them out of URLs and logs. `pending.summary` is what the owner approves and can include personal data. `sessionStorage` is a good place for all of it.
- The BRE-B key methods return most errors as `{ error }`, but throw `BloqueReturnUrlNotAllowedError` and `BloqueConfigError` like the approval errors.

## Re-register a passkey

When an approval fails with `BloqueApprovalInvalidError` and `reason: 'passkey_not_registered'`, or the person lost the device that holds their passkey, send them to register a passkey again. `identity.passkeys.createLink` returns a link to Bloque's identity portal that brings them back to `returnUrl` once they are done:

```typescript
const { url, expiresIn } = await user.identity.passkeys.createLink({
  returnUrl: 'https://myapp.com/settings/security',
});
window.location.assign(url); // expiresIn: e.g. '15m'
```

It needs the person's own session (a browser or React Native JWT); an API key or another kind of token gets `BloqueAuthenticationError` (403 `E_USER_SESSION_REQUIRED`). `returnUrl` follows the same rule as `approvalReturnUrl`.

| Error | Code | What to do |
| --- | --- | --- |
| `BloqueReturnUrlNotAllowedError` | 400 `E_RETURN_URL_NOT_ALLOWED` | Use a `returnUrl` whose origin your origin allows |
| `BloquePasskeyRegistrationUnavailableError` | 501 `E_PASSKEY_REGISTRATION_NOT_SUPPORTED` / 503 `E_PASSKEY_REGISTRATION_UNAVAILABLE` | `retryable: false`: this deployment does not register passkeys; not retried. `retryable: true`: retried automatically; retry later if it persists |
| `BloqueAuthenticationError` | 403 `E_USER_SESSION_REQUIRED` | Call it with the person's own session |
| `BloqueRateLimitError` | 429 | Too many links for this session (10 per hour by default). With `retry` on (the default), the SDK waits `Retry-After` (up to `maxDelay`) and retries before throwing |

## Errors

The error types are the same as for transfers, and every method on this page, the BRE-B key methods included, throws them: `BloqueApprovalRequiredError` (428), `BloqueApprovalInvalidError` (403), `BloqueApprovalExpiredError` (403) and `BloqueApprovalUnavailableError` (503). See the table in [Getting started](../start/getting-started#passkey-approvals).
